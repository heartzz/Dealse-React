# ADR 0004: Transactional in-app notifications

- **Status:** Accepted for the Web MVP
- **Date:** 2026-11-11
- **Decision owners:** DealSe product and engineering

## Context

DealSe needs a small engagement foundation for customers who follow stores or save offers, and a publishing confirmation for retailers. The initial Web MVP has a NestJS modular monolith and PostgreSQL as its system of record. There is no selected push, email, or SMS delivery provider, and such delivery would add credentials, retries, cost, consent and operational work.

## Decision

Implement an in-app notification inbox in PostgreSQL and store follows through NestJS. A notification is written in the same Prisma transaction as the deal publication/update that caused it. The database enforces recipient-scoped deduplication using `(user_id, dedupe_key)`, with the deal version in event keys.

Initial events:

- `RETAILER_PUBLISH_CONFIRMATION` for the retailer actor on successful publication.
- `STORE_ANNOUNCEMENT` for active customer-role users following the published store.
- `FAVOURITE_DEAL_UPDATED` for active customer-role users who saved a currently valid published deal that changes.

The inbox is available only to the authenticated recipient. Follow operations are customer-only and accept only currently public, verified, active stores. Notification text and internal destinations are generated by the server. Mark-read operations scope by both notification and caller ID and return not-found for another user's record.

## Consequences

- In-app notification state is reliable with the associated deal transaction; no notification is emitted if that transaction rolls back.
- Retries do not duplicate a publish event for the same deal version.
- Notifications are persisted in PostgreSQL and can be paginated/read without another service.
- Bulk fan-out is adequate for the early marketplace scale; growth may require a transactional outbox and background worker.
- Push, email, SMS, notification preferences, device tokens and delivery attempt tracking remain deferred until their consent, cost and provider requirements are approved.
- The additive migration `20261111100000_in_app_notifications` creates the `notifications` table. It does not alter or remove existing records.

## Alternatives considered

1. **Send email/push directly during deal publication:** rejected because it couples publication availability to an unconfigured external service and creates retry/partial-delivery behavior.
2. **Add Redis/BullMQ and an outbox worker now:** deferred; no external delivery channel exists, and a worker is not needed for an in-app-only inbox written in the same database transaction.
3. **Store notifications only in browser state:** rejected because state would not persist across sessions/devices and could not be permission-scoped centrally.

## Rollout and rollback

Apply using the normal additive Prisma migration deployment process after generation and PostgreSQL integration verification. Rollback before notification data exists may drop the table and its indexes/FKs. Once rows exist, prefer a forward fix or export them before any rollback. Do not apply the migration to production without a separately approved release task.
