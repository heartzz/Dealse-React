# DealSe web MVP readiness audit

**Audit date:** 2026-11-11  
**Scope:** Existing Next.js web experience, NestJS API, Prisma/PostgreSQL schema, authentication, media, CI and documented customer/retailer journeys.  
**Evidence rule:** A screen or route is not treated as proof that the complete journey works. API integration tests prove only the operations they exercise; public-route and crop-editor browser checks do not verify authenticated end-to-end journeys.

## Executive result

The repository contains a real Next.js + NestJS + Prisma/PostgreSQL marketplace slice: Supabase-backed web sign-in, customer discovery and favourites, retailer onboarding, store/product/deal management, an initial admin moderation workflow, and a local demo catalogue. NestJS integration tests cover authentication/roles and the retailer-to-customer deal lifecycle. This is more complete than the root README and `docs/backend-integration-plan.md` describe.

The repository is not yet a complete or production-ready Web MVP. The most important correctness gap found in the public API was that deal status and dates alone controlled visibility; pending retailers and unverified stores could publish offers that appeared publicly. The API now also requires an active retailer and an active store with a verification timestamp for publishing, public discovery, deal detail, store detail and favourites. That change follows the approved policy in `docs/architecture.md`; the admin workflow described below now provides the approval and moderation actions.

Admin review and moderation are implemented in NestJS and a `/admin` Next.js workspace, including customer offer reports, retailer/store approval, categories, offer holds and audit history. The current pass adds transactional in-app notifications and store follows with inboxes in the customer and retailer web workspaces, editable customer display name, and allowlisted discovery sorting. PostgreSQL integration tests verify these API flows; browser journeys, live Supabase/MFA and responsive screenshots remain unverified. Production object-storage credentials and deployment configuration are not present in the repository environment examined here. Redemption remains deliberately deferred under the earlier instruction not to implement coupon redemption.

### Classification summary

- **Partially implemented:** search filters have no price-range or retailer filter; the profile only edits display name and does not yet expose customer city/preferences.

## Security and environment findings

- NestJS verifies OIDC JWT signatures/issuer/audience via configured JWKS and then loads roles from PostgreSQL. Tests cover a valid test key, forged-key rejection, customer denial from retailer APIs, and role access.
- Retailer product/deal/store queries use retailer membership and retailer ID scoping; integration coverage includes another retailer being denied access to a deal.
- The previous public-deal check omitted retailer/store verification. The code change in this audit now gates publishing and public reads on `retailer.status=ACTIVE`, `store.status=ACTIVE`, and `store.verifiedAt IS NOT NULL`.
- The API configures global DTO validation. Admin routes check the PostgreSQL role and verified Supabase `aal2` assurance claim. Admin state updates and audit rows share a transaction; reports are unique per customer/deal. The admin MFA enrollment/step-up flow and API enforcement are implemented but not live-project verified.
- The media upload API has a per-user in-process limit and strict file size/MIME handling. There is no API-wide or cross-instance rate limiter yet. The public store endpoint uses the same active retailer/verified store gate as public deal discovery. Nearby discovery uses bound parameters for coordinates, category, city and search; PostGIS' geography GiST index can service the radius predicate. Browser geolocation is opt-in and coordinates are not persisted.
- `.gitignore` ignores `.env`, `.env.*` (except `.env.example`) and `*.local`. Local web config names include Supabase URL/publishable key and API URL; API config names include database and OIDC/JWKS settings. Values were not read or copied into this document.
- Local authentication configuration is present, but live Supabase registration/login and browser cookie/session behavior were not exercised in this audit. No service-role key should be added to the web environment.
- No production object-storage bucket/CDN or deployment secrets were identified. Production launch is blocked on those external resources and operational policies.
